FAQ

Common questions about dockerpatch. See docs.html for full API/architecture reference.

Does this replace Docker?

No. It wraps your existing docker binary. Every subcommand except install is passed straight through to the real binary unmodified, regardless of your installed Docker version.

Is it safe to run an install script without reviewing it first?

docker install <name> fetches and runs a published docker run command over HTTPS. If you want to review it first, fetch /scripts/<name>.txt yourself before running.

A script is asking me to type a password/token — is that normal?

Yes. Scripts that need a real credential (a database password, an API key, etc.) prompt for it interactively at install time rather than shipping a hardcoded placeholder value in the script text. Nothing is sent anywhere except straight into the docker run command as an environment variable.

Why does the server URL keep changing?

The hosted catalog server runs behind a Cloudflare quick tunnel, which issues a new hostname on every restart. tunnel-url.txt at the repo root always reflects the current one — clients fetch it at request time instead of hardcoding a URL.

Can I run my own catalog server instead of the hosted one?

The server component isn't published in this repository (kept private, not meant to be run by third parties as-is). If you want a self-hosted catalog, you'd need to write your own server implementing the same three endpoints documented in docs.html: /api/list, /api/info/<name>, and /scripts/<name>.txt.

How does submit.html decide what's junk?

New packages (both from the automated GitHub-search discovery process and manual submissions) are filtered for: non-Latin-script or placeholder-style descriptions, generic scaffold/coursework names, image tokens that aren't real pullable images, and names over 20 characters. None of this is perfect — it's a heuristic filter, not manual curation.

I got unsupported protocol scheme "" — what does that mean?

Your cached tunnel URL is stale. Re-run the install one-liner to refetch tunnel-url.txt.

I got package not found.

Either the name has a typo, or the package was renamed/removed since you last checked. Run docker install with no arguments to see the current list.

submit.html is stuck on "Searching GitHub..."

GitHub's unauthenticated code-search API is limited to 10 requests/minute. Wait a minute and try again.

How do I remove the patch?

Delete the wrapper binary and rename docker-real back to docker. See docs.html for the exact paths.

Why do some package names end in a number or a suffix like -someuser?

Multiple unrelated GitHub repos sometimes use the same generic name (e.g. two completely different tools both called "thor"). Rather than silently merging them under one entry, the second one discovered gets a suffix — usually derived from the source repo's owner (thor-someuser) — so they stay distinguishable as separate, real, unrelated tools.

What license is this under?

MIT — use it, fork it, self-host your own catalog server against the same client, no restrictions.

Are the categories accurate?

Mostly heuristic. Categorization tries the source repo's real GitHub topics first where available, and falls back to keyword matching against the name/description otherwise. Some packages land in "Other" simply because neither approach had enough signal.

Can I trust every package in the catalog?

Treat it the same as any other package registry: the scripts run real, unmodified docker run commands sourced from public GitHub repos, but nothing here is manually security-audited per package. Review a script before running it if you're installing something unfamiliar.

Does docker install need network access?

Yes — it fetches the current tunnel URL, the catalog, and the script text over HTTPS each time, rather than caching anything locally, so it always reflects the current catalog.

What platforms does the patch run on?

Anywhere the real docker CLI and Go can run — Linux and macOS natively, Windows via WSL2. It's a wrapper around your existing Docker installation, not a separate runtime.

Does it work with Docker Desktop?

Yes. The wrapper only intercepts the install subcommand at the CLI level; it doesn't care whether the underlying daemon is Docker Desktop, Docker Engine, or another Docker-CLI-compatible setup.

Does it work with Podman?

Only if you're using Podman's docker-compatible CLI alias. The wrapper shells out to whatever binary it renamed to docker-real — if that's Podman under an alias, non-install commands pass through fine, but this hasn't been specifically tested against Podman.

What if a file named docker-real already exists before I install?

install.sh will refuse to overwrite an existing docker-real rather than risk clobbering something — if you see that error, check what that file already is before proceeding.

Can I install multiple packages in one command?

No — docker install <name> takes exactly one package at a time. Run it multiple times for multiple packages.

Does installing a package pull the image automatically?

Yes — the generated script's docker run command pulls the image itself if it isn't already present locally, same as running that command by hand.

What happens if a package's underlying image was deleted or moved on its registry?

The install script will fail at the docker run step with a normal Docker pull error. The catalog doesn't currently re-verify that every image still resolves after it's added.

Can I see a package's exact command before installing it?

Yes — fetch /scripts/<name>.txt yourself (see docs.html) to read the full script before running docker install <name>.

Does the catalog include Kubernetes manifests?

No. Every entry is a single docker run invocation — no Compose files, Helm charts, or Kubernetes YAML.

Why "docker install" instead of a separate CLI tool?

So there's nothing new to remember or install separately — if you already know docker, you already know the interface. It's meant to feel like it should have always been part of Docker.

Is there a docker uninstall?

Not currently. You'd remove the container the same way you would any other: docker stop <name> then docker rm <name>.

Is there a docker update <name> to re-pull the latest image?

Not yet. For now, re-run the install script manually, or docker pull the image and recreate the container yourself.

Does the patch modify my Docker daemon configuration?

No. It only replaces the docker CLI binary with a wrapper; the daemon itself (dockerd) and its configuration are untouched.

Will installing the patch affect my existing containers?

No — existing containers keep running exactly as they were. The patch only affects how the docker command behaves going forward.

Can I pin a specific image tag instead of always getting :latest?

Not through the catalog directly today — fetch the script text, edit the tag yourself, and run it manually if you need a pinned version.

Does dockerpatch collect usage analytics?

The server logs requests for its own operation (debugging, catching abuse), but there's no separate analytics/tracking pipeline built into the CLI or client.

Is dockerpatch affiliated with Docker, Inc.?

No. It's an independent, unofficial wrapper around the Docker CLI.

Why isn't the package I want in the catalog?

Either it hasn't been discovered yet by the automated GitHub-search process, or it got filtered out as junk/malformed. Submit it yourself via submit.html.

Can I ask for a package I submitted to be removed?

There's no self-service removal — open an issue on the GitHub repository to request it.

What happens if two catalog packages point at the same underlying image?

The discovery process dedupes new finds against known images before adding them, but pre-existing near-duplicates (same tool, different source names) can still occasionally slip through and get cleaned up in a later pass.

Could junk packages ever get re-added after a cleanup pass?

Only if the same repo turns up again in a fresh discovery run and the current junk filters don't happen to catch that particular pattern. The filters improve over time but aren't exhaustive.

Does submit.html require a GitHub account?

No — it only reads public repo data via GitHub's API through a private proxy; you don't authenticate as yourself.

Can I submit a private repo?

No — the search proxy only has access to what GitHub's public code-search API can see, which excludes private repositories.

What if my repo's docker run command spans multiple lines with backslashes?

That's handled — both the automated discovery process and the submit flow parse backslash-continued multi-line commands, not just single-line ones.

Why does every install script echo "Installing..." and "...installed"?

Just visible feedback so you can tell the script actually ran and reached the end, rather than silently doing nothing on failure.

Does docker install require sudo?

Only if your regular docker usage already requires sudo on your system — the wrapper doesn't change your existing permission model.

Is there a native Windows build (not via WSL2)?

Not currently — Windows support goes through WSL2 running a Linux environment.

What Go version is needed to build the patch from source?

Whatever's current when you build — check patch/go.mod in the repository for the exact minimum version pinned.

Can I build install.sh's result from source instead of piping curl to bash?

Yes — clone the repo, cd patch && go build, then manually rename your existing docker binary to docker-real and put the built wrapper in its place.

Does the wrapper break docker-compose?

No — compose isn't the intercepted subcommand, so it passes straight through to the real Docker CLI/plugin unmodified.

Does the wrapper break docker buildx?

No, same reasoning — only the literal install subcommand is intercepted; everything else, including buildx, goes straight to docker-real.

What happens if I run install.sh twice?

The second run will find docker-real already present and refuse to proceed rather than risk wrapping the wrapper.

Can I use dockerpatch on an air-gapped machine?

No — both the catalog lookup and the install script execution require live network access to the hosted server. There's no offline/cached mode.

Why is the site dark-themed only?

Just a design choice — there's no light theme toggle currently.

Is there a way to suppress the "installed" confirmation message?

Not as a CLI flag — you'd need to edit the specific package's script yourself if you want quieter output.

What is the install-id actually used for?

It's a deterministic short identifier (first 8 bytes of sha256(name)) for referencing a package outside the normal name-based flow — mainly useful for findinstalls.html-style lookups.

Does findinstalls.html work offline?

No — it queries the live catalog server the same way the CLI does.

Does dockerpatch verify image signatures or checksums?

No — it runs the same docker run command you'd run yourself, with the same trust model as pulling any image directly from its registry.

What happens if the tunnel goes down mid-install?

The script-fetch step will fail with a network error. Nothing partially applies — either the full script is fetched and run, or nothing runs at all.

Is there a status page for server uptime?

Not currently — there's no separate status dashboard beyond the server actually responding to requests.

Can I mirror the catalog to my own CDN?

Nothing stops you from polling /api/list and /scripts/<name>.txt yourself and re-serving them, but there's no built-in mirroring/export feature.

Why not just search Docker Hub directly instead of using this catalog?

Docker Hub search finds images, not ready-to-run commands with the right ports/volumes/env vars already worked out — that's the actual value of a catalog entry here.

How is this different from an Awesome-Selfhosted-style list?

Those are curated reading lists you browse manually. This is meant to be actionable from the terminal directly — docker install <name> and it's running, no copy-pasting a command from a README.

Does the categorizer use an LLM or AI call?

No — it's plain keyword/heuristic matching against the name and description, plus a lookup against the source repo's real GitHub topics where available. No AI API calls involved.

Are non-Latin-script tools excluded from the catalog entirely?

Entries with non-Latin-script descriptions/names get filtered at discovery time, since the resulting catalog text would be unusable for most users browsing in English — this is a practical filter on the catalog text, not a judgment on the tools themselves.

What happens to a submitted package that gets rejected as junk?

It simply isn't added — no partial entry is created, and nothing is retained from a rejected submission.

Can dockerpatch be used inside a CI pipeline?

Nothing prevents it technically (it's just shell scripts calling docker run), but it isn't designed or tested for unattended CI use — treat it as an interactive/manual tool for now.

Where do I report a bug?

Open an issue on the GitHub repository.
