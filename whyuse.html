Why dockerpatch?

What this actually saves you, in plain terms.

The problem it solves

Standing up a self-hosted app usually means: find the project, find its README, find the actual docker run command buried in it, figure out which ports/volumes/env vars you need, then run it. That's several minutes and a few tabs for something that should be one line.

docker install jellyfin

That's the whole workflow. It fetches the real, working docker run command for that project and runs it.

What it isn't

dockerpatch

A thin wrapper around your existing docker CLI. Only install is new — every other command behaves exactly as it always has.

Not a new runtime

No new daemon, no new config format, no replacement for Docker itself. If you already know docker, you already know this.

Who this is for

Anyone who self-hosts more than one or two things and is tired of re-deriving the same docker run incantation from a README every time. If you already have a personal collection of bookmarked install commands, this is that collection, searchable, shared, and growing.

What you're trusting

Same trust model as pulling any image and running any command yourself — every script is a plain, readable docker run line sourced from a real public repository. Nothing is obfuscated, and you can read /scripts/<name>.txt before running anything. See the FAQ for the details on how junk/malformed entries get filtered out.

A concrete before/after

Before: you hear about a self-hosted RSS reader called Miniflux. You Google it, land on the GitHub repo, scroll past the badges and the feature list to find the "Docker" section, notice it wants a Postgres container too, copy both commands, realize you need to set an admin password env var, look up what that variable is actually called, then finally run both containers.

After:

docker install miniflux

The port mapping, the env vars, and the exact image tag are already worked out from a real, working example — you just get prompted for the one thing that's actually yours to decide (a password), instead of hunting for it in prose.

How it compares to other options

vs. copying commands from READMEs

This is exactly that, just pre-done. The catalog exists specifically so you don't have to be the one parsing someone's install instructions each time.

vs. Docker Compose stacks

Compose is the right tool once you're running several coordinated services long-term. This is for the "I just want this one thing running right now" case — a single command, not a stack file to maintain.

vs. a GUI app store (Portainer templates, Unraid, CasaOS)

Those are great if you're already running that specific platform. This works from any terminal with Docker installed — no separate management UI to stand up first.

vs. an Awesome-Selfhosted-style list

Those are curated reading lists — great for discovery, but you still end up copy-pasting a command out of a linked README. This is meant to be acted on directly from where you found it.

Where the catalog actually comes from

It's not hand-typed one entry at a time. An automated process searches GitHub for real docker run -d -p ... commands already committed in public repositories, extracts the actual working command (not a placeholder), and pulls the project's own description for context. A junk filter runs before anything is added — rejecting things like coursework/tutorial repos, broken or self-referential commands, names that are just a hex hash, and non-Latin-script descriptions that wouldn't be readable in the catalog anyway. You can also submit a specific repo yourself via submit.html if the automated search hasn't found it yet.

The install-time credential prompt

Some real-world docker run commands hardcode an example password or API key directly (e.g. -e password=changeme123) because that's what the original README showed. Rather than ship that placeholder as-is, or silently drop it, dockerpatch detects credential-looking environment variables and prompts you for a real value interactively at install time — so you get a working, personalized container instead of one running on a copy-pasted example secret.

What happens after you type the command

docker install <name> does exactly three things, every time: fetch the current catalog, resolve the package name to its script, and run that script. Nothing is cached, nothing is guessed — you always get the current, live version of a package's install command, the same one anyone else typing that command right now would get.

A catalog that keeps growing

The catalog isn't a fixed snapshot — it's continuously expanded by an automated discovery process running against GitHub, plus direct community submissions through submit.html. Every category from media servers to databases to home-automation tools to dev/CI tooling picks up new real-world entries over time, so a search that comes up empty today can turn up something next time.

Everything organized, browsable, and searchable

The homepage catalog isn't just a flat list — every package is tagged with a real category (media & streaming, databases, monitoring, networking, security, home automation, and more), so you can browse by what you're actually looking for instead of scrolling an alphabetical dump. Categorization pulls from the source repository's own GitHub topics where available, falling back to keyword matching, so tags stay grounded in real signal rather than guesswork.

Deterministic, shareable install IDs

Every package also gets a short, stable install-id (derived from its name, so it's the same every time). That means you can reference a specific package by ID — handy for sharing a link to exactly the thing you mean via findinstalls.html — without worrying about ambiguity if names ever overlap.

Nothing to install to get started

There's no separate app, daemon, or account needed beyond Docker itself, which you already have if you're reading this. install.sh patches your existing docker binary in one step, and from that point on docker install <name> just works alongside every command you already use daily.

Open, forkable, and yours

dockerpatch is MIT licensed — read the source, fork it, adapt the client to point at your own catalog, or just use it as-is. Nothing about it is locked to a specific vendor or hosting provider.

Built for the way people actually self-host

Most self-hosters don't run one carefully-planned stack — they try things. A new media server one weekend, a monitoring dashboard the next, a note-taking app after that. dockerpatch is built around that reality: low commitment per try, a real working command every time, and a catalog wide enough that the next thing you want to try is probably already in it.
